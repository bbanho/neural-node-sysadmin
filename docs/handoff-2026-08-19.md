# NEXUS — Sessão 2026-08-19 — Estabilização headless (crashes silenciosos)

> O que estava acontecendo: vários crashes silenciosos (8 boots em 2 dias), sessões de 20-40min.
> Diagnóstico feito e corrigido nesta sessão, em cima do handoff de 2026-08-17.
> Próxima leitura obrigatória para quem assumir: `~/handoff-2026-08-17.md` (estado do BD + PRs #40/#41) e este arquivo (o que mudou desde então).

## 1. Diagnóstico dos crashes silenciosos

1. **Postgres OOM (causa confirmada):** container `nexus-postgres` com `mem_limit=256M` é pequeno demais. O cgroup do container matou o processo `postgres` no boot (dmesg: `Memory cgroup out of memory: Killed process 3227 (postgres)`, rss ~249MB). A partir de 2026-08-19 o limite subiu.
2. **Swap thrash do ollama (causa de lentidão/stall):** `llama-server` da qwen2.5-coder:7b rodava `-np 2` + `-c 8192`. O KV cache transbordava a VRAM (6GB) → offload parcial p/ CPU → cgroup 3G estourado → swap zram (pico 1.6G swap). Resultado: gerações de L2 em 58-63s com `0.0 tok/s`.
3. **Reboots limpos:** os boots antigos terminaram com `systemd-reboot` gracioso (não kernel panic) — sessões interativas presencial terminadas à mão. Não é bug; mas o OOM do postgres a cada boot era um crash de verdade.

## 2. Mudanças aplicadas (NÃO refazer)

`/var/home/bruno/repos/NEXUS/compose.yaml`:
- `postgres.deploy.resources.limits.memory`: `256M` → `768M` (aplicado também live via `docker update --memory 768m --memory-swap 1536m nexus-postgres`, sem restart).
- `ollama` env: `OLLAMA_NUM_PARALLEL: "2"` → `"1"` e adicionado `OLLAMA_CONTEXT_LENGTH: "4096"` (KV ~4x menor → cabe na GPU → fim do swap thrash). Ollama recriado com `docker compose up -d --no-deps --force-recreate ollama`.

## 5. Reparo preventivo (self-healing) — adicionado 2026-08-19

- **`nexus-healer`**: systemd `timer` a cada 60s (+90s pós-boot), roda script root `/usr/local/sbin/nexus-healer.sh`.
  - Reconcilia os 6 containers (`docker compose up -d` se algum cair) · restaura containers `unhealthy` · reinicia engine se `/pipeline-status` morrer · rastreia OOM em dmesg (`/var/lib/nexus-healer/last_oom_count`) · avisa se `MemAvailable < 1G` · loga em `/var/log/nexus-healer.log`.
  - Crash-loop guard: >3 restarts/min logs PANIC e pausa reparo do engine.
- **Boot blindado**: default `multi-user.target` + **gdm desabilitado** (`display-manager.service` removido; `sdg on` segue funcionando manualmente) → headless garantido no próximo boot. docker/tailscaled/sshd `enabled`, hermes-gateway user unit `enabled` + linger.
- Testado: primeiro run foi no-op (`OK stack 6/6`), sem ação falsa.

## 6. Security hardening tailnet (2026-08-19)

- **Loopback-only**: postgres 5432, qdrant 6333/6334 e gateway 8010 agora bind `127.0.0.1` (compose). Engine 8000: bind hardcoded 0.0.0.0 (`main.rs:378`) → bloqueio nft priority `filter -100` (`/etc/nftables.d/nexus-blocktail.nft`, unit `nexus-blocktail.service`): `iifname "lo" accept` + drop com counter de `tcp {5432,6333,6334,8000,8010}` em qualquer entrada não-loopback (tailnet E LAN, v4/v6). Loopback preservado (healer/mcp/engine locais OK).
- **Expostos à tailnet (intencional, sem auth)**: só `11434` (ollama) e `7474` (MCP POST /sse). Docs atualizados (AGENTS-CONSUMERS/AGENTS.md/GUIA).
- **Por que firewalld não bastou**: tailscale `ts-input` aceita tudo do `tailscale0` (priority 0) antes do firewalld (priority +10) no hook input → regras de zona nunca veem o tailnet; o bloqueio precisa rodar com prioridade menor (nft -100).
- **Pendente**: exit node anunciado no tailscale; sshd password auth `j` ativo (recomendado: só `tailscale ssh`).

## 7.5 Hardening anti-OOM de HOST (sessão 2026-08-19 23h)

O OOM de **cgroup** (postgres 256M) já estava resolvido, mas o boot que abriu esta sessão
revelou o **OOM de host**: `system.slice: The kernel OOM killer killed some processes`
(22:14:56 no boot anterior) + journal corrompido + `/boot` com dirty bit = nó ficou
inacessível/derrubado. `systemd-oomd` só reage a pressão sustentada (>30s); a rampa é rápida.

**Fix aplicado e commitado** em `~/repos/neural-node-sysadmin` (git `8c9e0bb`, fonte de
verdade + `install.sh` idempotente, já aplicado neste boot):
- `OOMScoreAdjust=-900` em drop-ins de `sshd/tailscaled/containerd/docker`
  (`/etc/systemd/system/*.service.d/oom-protect.conf`) — o kernel OOM passa a escolher
  vítima entre os containers (restart automático) e NUNCA a porta de acesso/runtime.
- `/etc/sysctl.d/90-neural-node-memory.conf`: `vm.swappiness=60` + `vm.page-cluster=0`
  → o swap zram absorve picos antes do kernel sair matando.
- Healer v2 (`/usr/local/sbin/nexus-healer.sh`): detecta OOM de **host** E cgroup e
  emite `logger -p daemon.emerg` (silencioso → alto), além de corrigir o bug do
  `last_oom_count`. Validado: `OK stack 6/6`, `last_oom_count=0`.

Verificação pós-fix: `systemctl show -p OOMScoreAdjust {sshd,tailscaled,containerd,docker}`
→ `-900`; `swappiness=60`; `page-cluster=0`.

**Observado, não bloqueia**: `ata1 FLUSH CACHE EXT ABRT` transiente num boot (link resetou,
`EH complete`). Vigiar o SSD 360GB com `smartctl -a /dev/sda` de vez em quando.
